# Phase 4, Sub-project #1 — PWA Installability: Design

**Status:** Approved, ready for implementation planning.
**Depends on:** Phase 2 (Frontend Core) and all of Phase 3 (local learning tools) — complete and merged/pushed to `origin/master`.
**Scope boundary:** the first of three sub-projects decomposing "Phase 4 — PWA + Offline" (`site-build-docs/00-BUILD-README.md`, `05-PWA-AND-DEPLOYMENT.md`). Sub-project #2 (offline caching of topic content) and sub-project #3 (performance/code-splitting) come after this one.

## Goal

Make the app installable — a real manifest, generated icons, a service worker registered via `vite-plugin-pwa`, and an in-app install button — without yet caching anything beyond the built app shell.

## Corrections to the original plan doc

Explored before designing; three assumptions in `05-PWA-AND-DEPLOYMENT.md` don't match the actual codebase and are corrected here rather than silently followed:

- **No KaTeX exists in this app.** Formulas are pre-rendered PNG images (already `loading="lazy"` in the generated HTML) — the doc's "dynamic KaTeX import" optimization item is moot, nothing to do.
- **No custom webfont is actually loaded.** CSS declares `font-family: 'Heebo', system-ui, sans-serif` but there is no `@font-face`, no Google Fonts link, and no `.woff2` file anywhere — it silently resolves to `system-ui` today. The doc's "strip duplicate ttf/woff" item doesn't apply (there's nothing to strip); whether to actually load Heebo is out of scope for this sub-project and left for sub-project #3 to decide if it becomes relevant.
- **No logo asset exists.** The doc assumes an existing "Σ" logo; the app only uses a 🧠 emoji (in `Header.tsx`). This design generates real icon files from that emoji instead (see below) rather than introducing a new, unused brand mark.

## Out of scope

Runtime caching of topic content/images and any offline-fallback UX — all sub-project #2. (The static data JSON files — `topics.clean.json`/`modules.json`/`search-index.json` — are already precached as part of this sub-project's app-shell bundle, since they're `import`ed as ES modules rather than fetched separately; see the correction in Section 3.) Per-route code-splitting and the `<500KB` first-load target — sub-project #3. Supabase (Phase 5). Actual hosting deploy (Phase 6).

## Section 1: Icon assets

No image-rendering tool exists in this repo today, and rasterizing an emoji reliably needs real emoji artwork — drawing the character via a font is inconsistent across SVG rasterizers for color emoji.

- Add **`twemoji`** (Twitter's open-source emoji SVGs, CC-BY 4.0 — attributed in a new `NOTICE` file at the repo root: `"Emoji graphics from Twemoji (https://github.com/twitter/twemoji), CC-BY 4.0."`) and **`sharp`** (SVG→PNG rasterizer, prebuilt binaries, no native build step) as **devDependencies only** — neither ships in the app bundle.
- A one-time script, `kb-app/scripts/generate-icons.mjs`, takes Twemoji's 🧠 SVG (Unicode codepoint `1f9e0`) and rasterizes it to:
  - `kb-app/public/icons/icon-192.png`, `kb-app/public/icons/icon-512.png` — the glyph on a transparent background, scaled to fill the canvas.
  - `kb-app/public/icons/maskable-512.png` — the same glyph centered at ~80% scale over a solid `#0f1220` square (the standard "safe zone" convention for maskable icons, so Android's shape mask doesn't crop the brain at the edges).
  - `kb-app/public/favicon.png` (32×32) — the app has no favicon today; this adds one.
- Run once during this sub-project's implementation; the generated PNGs are committed to git like any other static asset, not regenerated by `npm run build`.

## Section 2: `manifest.webmanifest` + meta tags

`kb-app/public/manifest.webmanifest`:
```json
{
  "name": "מסד ידע — AI Engineer",
  "short_name": "מסד ידע",
  "lang": "he",
  "dir": "rtl",
  "start_url": "/",
  "display": "standalone",
  "background_color": "#0f1220",
  "theme_color": "#0f1220",
  "icons": [
    { "src": "/icons/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png" },
    { "src": "/icons/maskable-512.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
  ]
}
```
`#0f1220` matches the existing hardcoded `<meta name="theme-color">` in `kb-app/index.html` today (itself matching the dark-theme `--kb-bg` token). The manifest can only declare one static color, so it stays dark-first regardless of the visitor's light/dark preference — consistent with what's already shipped.

`kb-app/index.html` gains:
- `<link rel="manifest" href="/manifest.webmanifest">`
- `<link rel="icon" href="/favicon.png">`
- `<meta name="apple-mobile-web-app-capable" content="yes">`
- `<link rel="apple-touch-icon" href="/icons/icon-192.png">`

## Section 3: `vite-plugin-pwa` wiring

Add **`vite-plugin-pwa`** as a devDependency — it generates the service worker at build time via Workbox; nothing is hand-written. In `kb-app/vite.config.ts`:

```ts
VitePWA({
  registerType: 'autoUpdate',
  manifest: false, // a static public/manifest.webmanifest is already shipped (Section 2)
  includeAssets: ['favicon.png', 'icons/*.png'],
  devOptions: { enabled: true }, // lets the SW be tested under `npm run dev`, not only preview
  // workbox.globPatterns defaults to the built JS/CSS/HTML app shell — that
  // IS "precache app shell" from the spec, and needs no extra config.
})
```

**Scope boundary, explicit:** this sub-project's service worker precaches only the app shell (the JS/CSS/HTML Vite already builds) — `vite-plugin-pwa`'s default behavior. It does **not** cache any `topic-content/`/`topic-assets/` file, and does **not** make a previously-read topic's HTML/images work offline — that is entirely sub-project #2. This sub-project's offline story is narrower than sub-project #2's, but not as narrow as originally assumed here: `topics.clean.json`/`modules.json`/`search-index.json` are `import`ed as ES modules (not fetched as separate files), so Vite inlines their content into the main JS bundle — which this sub-project's app-shell precache does include. In practice, Home and search work offline once installed; only Reader's per-topic HTML/images (fetched from `topic-content/`/`topic-assets/`, explicitly excluded from this sub-project's precache) remain unavailable offline until sub-project #2 lands. *(Correction added after the final review of this sub-project — the original text above this note assumed the data files were excluded from the precache; they are not, because they were never separate files to begin with.)*

`kb-app/src/main.tsx` registers the service worker via the plugin's virtual module:
```ts
import { registerSW } from 'virtual:pwa-register';
registerSW({ immediate: true });
```
This import only resolves under Vite's own build/dev pipeline. Vitest (jsdom) never executes `main.tsx` in any existing test, so the test suite is unaffected.

## Section 4: Install button

New `kb-app/src/hooks/useInstallPrompt.ts` (matches the existing `src/hooks/useGridKeyboardNav.ts` convention):
- Listens for `window`'s `beforeinstallprompt` event, calls `event.preventDefault()`, and stores the event in state (not a ref — the component must re-render once it becomes available).
- Listens for `appinstalled` to clear the stored event (so the button disappears once installed).
- Returns `{ canInstall: boolean; promptInstall: () => void }` — `promptInstall` calls the stored event's `.prompt()`, awaits `.userChoice`, then clears the stored event regardless of the outcome (a captured `beforeinstallprompt` event can only be prompted once).

`kb-app/src/components/layout/Header.tsx` renders a new button — "📲 התקן אפליקציה" — next to `ThemeToggle`, rendered only when `canInstall` is `true`. No fallback UI on browsers that never fire `beforeinstallprompt` (Firefox, Safari) — there is no reliable cross-browser install-detection API, so this matches "show when available" and keeps scope tight.

## Testing

- `useInstallPrompt.test.ts`: dispatching a mock `beforeinstallprompt` event flips `canInstall` to `true`; calling `promptInstall()` calls `.prompt()` on the stored event and clears state afterward; a mock `appinstalled` event clears `canInstall`.
- `Header.test.tsx` addition: the install button is absent by default, appears after a `beforeinstallprompt` event is dispatched, and calls `promptInstall` on click.
- Manual, not testable in jsdom: `npm run build && npm run preview`, install on real Android/desktop Chrome, confirm standalone launch and that the icon is not cropped as maskable on Android; iOS "Add to Home Screen" uses the apple-touch-icon.

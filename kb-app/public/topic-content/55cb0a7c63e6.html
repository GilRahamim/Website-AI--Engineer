📋 הגדרה

Plan Mode הוא permission mode שבו ה-agent יכול רק לקרוא — אין edits, אין writes, אין Bash הרסני. ה-agent סוקר את הקוד, מציע תוכנית (plan), והמשתמש מאשר אותה — רק לאחר מכן מתחיל ביצוע בפועל.

⚙️ איך זה עובד

  • ב-SDK: permission_mode='plan'.
  • ה-agent מציע תוכנית; המשתמש מאשר; ה-runtime משדרג הרשאות ל-acceptEdits (או דומה) באמצעות כלי ExitPlanMode.

🎯 למה זה חשוב

  • מונע מהמודל 'לתקוף' תיקון שגוי לפני בדיקה.
  • איטרציה זולה על הגישה (approach) לפני תשלום על edits בפועל.
  • audit trail — התוכנית היא 'חוזה' (contract) שניתן לעיין בו אחר כך.

💻 דמו מלא — Code-Review Plugin (Skill + Sub-Agents + Hook + Plan Mode)

Plugin המריץ סקירת PR מלאה: Skill review-pr (נוהל אורקסטרציה) → מפזר ל-2 sub-agents (security-reviewer, style-reviewer) שכל אחד קורא diff בקונטקסט מבודד ומחזיר punch list → Hook מסוג PreToolUse חוסם כתיבה ל-main → Command /review הוא נקודת הכניסה. ה-agent ההורה ממזג את שני ה-punch lists לסקירה מאוחדת.

🏛️ מחסנית ה-Agent המלאה (Full Agent Stack)

שכבהתיאור
Plugin layerחבילה מנוהלת-גרסאות: skills + agents + hooks + commands
Skill layerPlaybooks: SKILL.md, scripts, templates
Sub-agent layerחלונות קונטקסט מבודדים, תפקידי מומחה
SDK / Runtimeלולאת query(), hooks, permission mode, streaming
Tool layerBash, Read, Edit, MCP servers, web fetch

Hooks חוצים את כל השכבות — guardrails דטרמיניסטיים מעל מודל non-deterministic.

🛠️ דפוסים ואנטי-דפוסים (Patterns & Anti-Patterns)

  • Fan-out research — פתיחת N sub-agents במקביל, מיזוג סיכומים. חוסך קונטקסט וזמן-קיר.
  • Deterministic gate — hook מסוג PreToolUse שמריץ typecheck לפני כל Edit; חוסם commits שבורים.
  • Plan-then-execute — permission_mode='plan' → אישור משתמש → שדרוג ל-acceptEdits. זול לתקן כיוון.
  • Plugin per workflow — plugin אחד לכל job הנדסי חזרתי (review, release, onboard). מנוהל-גרסאות, ניתן לשיתוף.
  • ❌ אנטי-פטרן: לדחוס הכול ל-agent הראשי — הקונטקסט מתנפח, המודל סוטה.
  • ❌ אנטי-פטרן: לסמוך על hooks לביצוע לוגיקה עסקית — הם שומרים (guards), לא features.

🧠 שאלות ראיון נפוצות

ש: מה ה-ExitPlanMode tool עושה בדיוק בתהליך plan-then-execute?

ת: הוא המנגנון שבו ה-agent 'מציע' את התוכנית למשתמש; לאחר אישור המשתמש, ה-runtime משדרג את permission mode מ-'plan' (read-only) למצב שמתיר edits — כך שהביצוע בפועל מתחיל רק אחרי אישור מפורש.

ש: בדמו ה-code-review plugin, מי מבצע את המיזוג הסופי של שני ה-punch lists?

ת: ה-agent ההורה (parent) — לאחר ששני ה-sub-agents (security-reviewer, style-reviewer) מחזירים כל אחד סיכום קצר בקונטקסט המבודד שלו, ה-agent ההורה ממזג את שניהם לסקירה מאוחדת אחת ופועל לפי הוראת ה-PROMPT.

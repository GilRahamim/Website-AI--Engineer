🎯 Case Studies 1–5

  • 1. תרגום שיווקי EN→ES, 50/יום → Simple LLM. Stateless, בלי retrieval; fine-tune רק אם ה-brand voice סוטה.
  • 2. Q&A משפטי על 10,000 חוזים → RAG. הקורפוס גדול מ-context; חייבים לציין מקור; fine-tune שגוי — עובדות משתנות.
  • 3. "הזמן טיסה NYC→TLV מתחת ל-$800, ניתנת לביטול" → Single Agent. רב-שלבי: חיפוש, סינון, השוואה, הזמנה — דורש tools + תכנון.
  • 4. דו"ח שוק: מחקר + מתחרים + פיננסים + מצגת → Multi-Agent. מומחים מקבילים, orchestrator ממזג — יותר מדי לקונטקסט אחד.
  • 5. קליטת עובד: Okta → Slack → GitHub → Jira בסדר קבוע → Flow. שלבים קבועים, אין שיקול דעת באמצע; LLM רק בקצוות.

🎯 Case Studies 6–10

  • 6. בדיקת נגישות WCAG 2.1 AA בכל PR → Skill. פרוצדורלי, חזרתי, בלי שליפה חיה — אורזים צ'קליסט + דוגמאות.
  • 7. סיווג כרטיסי תמיכה ל-200 קטגוריות, דיוק 98% → Fine-Tune. נפח גבוה, צר, תוויות יציבות — עדיף על RAG כאן.
  • 8. נציג מכירות: "הצג 5 אינטראקציות אחרונות של Acme ב-Hubspot" → MCP (Hubspot). CRM חי, שיחתי — לא RAG, הנתונים חיים.
  • 9. סיכום מנהלים שבועי מ-Slack+Linear+GitHub → Flow + MCPs. Cron → MCPs שולפים → LLM מסכם → פוסט. דטרמיניסטי.
  • 10. דיבוג תקרית production: logs → השערה → query → תיקון → פוסט-מורטם → Multi-Agent + MCPs. חוקר + כותב; open-ended = agent, לא flow.

⚠️ שאלת מלכודת לתלמידים

"צ'אטבוט עונה על שאלות מדיניות HR." תשובה שגויה: fine-tune. תשובה נכונה: RAG — מדיניות משתנה, נדרשים ציטוטים, fine-tune 'אופה' מידע מיושן (stale) בתוך המודל.

🧠 שאלות ראיון נפוצות

ש: מה ההבדל בין case study #2 (RAG על חוזים) ל-#7 (Fine-Tune על סיווג כרטיסים) שגורם לבחירה הפוכה?

ת: ב-#2 העובדות (תוכן החוזים) משתנות וצריך לצטט מקור — fine-tune יבייק מידע מיושן. ב-#7 המשימה צרה ויציבה (200 קטגוריות קבועות, נפח גבוה) — fine-tune מתאים כי אין צורך ב'ידע חדש', רק בדיוק סיווג גבוה וזול ב-inference.

ש: מדוע 'צ'אטבוט HR' היא שאלת מלכודת קלאסית?

ת: כי האינטואיציה הראשונית היא 'fine-tune את ה-bot על מדיניות החברה' — אך מדיניות HR משתנה ודורשת ציטוט מקור מדויק (auditability); RAG פותר את שניהם, ו-fine-tune היה אופה תשובות מיושנות שלא ניתן לעדכן בלי אימון חדש.
